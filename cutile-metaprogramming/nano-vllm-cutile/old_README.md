# Metaprogramming with Semiformal Design Patterns for GPU Kernel development

이 프로젝트는 반정형 설계 언어(Semiformal Design Patterns, SDP)를 핵심 매개체로 활용하여 인간 연구자와 AI 에이전트 간의 의미론적 지식 기반(Semantic Knowledge-Base)을 구축하고, 이를 통해 저수준 GPU 커널(cuTile/CUDA)을 체계적으로 개발하는 시스템 아키텍처 및 에이전트 워크플로우를 실증합니다.

## 🎯 The Dual-Agent Paradigm

LLM 에이전트는 설계 언어(DSL)를 통해 동기화되는 두 가지 특화된 역할로 분리되어 작동합니다.

- **System Engineer (Architect):** 상위 수준의 SKILL과 아키텍처를 설계하고, Design Spec을 정의하며, 하위 모델이 준수해야 할 시스템 모델(System Model)과 물리 법칙(제약 사항)을 규정합니다.
- **Kernel Engineer (Executor):** 구체화된 컨텍스트를 바탕으로 저수준 GPU 커널(cuTile) 코드를 구현하고, 통제된 환경에서 에러 없는 실험과 성능 프로파일링을 수행합니다.

## 📚 Vertical Knowledge Architecture (지적 자산의 복리 성장 체계)

에이전트를 활용해 지적 자산을 지속적으로 확장하기 위해, 횡적 연결을 배제한 **엄격한 수직적 계층형 지식 아키텍처**를 구축합니다. 이 지식 베이스를 버전 관리 시스템(Git)과 연동하여 에이전트가 스스로 개선하게 함으로써, 시간이 지날수록 작업 품질과 생성 속도가 기하급수적으로 향상되는 지식의 복리 효과를 창출합니다.

1. **Level 3 (Meta-Skills Layer):** 에이전트의 역할, 프로젝트 방향성, 그리고 하위 SKILL들의 오케스트레이션 및 평가 기준을 정의합니다. (무엇을, 언제 할 것인가)
2. **Level 2 (Procedural Layer - SKILL.md):** 반복 가능한 워크플로우와 구체적인 스킬셋을 모듈화합니다. (어떻게 할 것인가)
3. **Level 1 (Constraint Layer - DESIGN.md, CONTRACT.md):** 시스템 환경, 메모리 레이아웃, 성능 제약(Invariants) 및 금지된 코드 패턴(Anti-patterns) 등 시스템 모델을 정의합니다.
4. **Level 0 (Codebase Layer):** 실제 실행 가능한 아티팩트(Python/cuTile 코드) 및 대상 레퍼런스입니다.

> [참고] **Composable SKILL.md (에이전트 스킬 프레임워크)**
> 각 SKILL은 특정 작업을 수행하기 위한 지침과 리소스가 패키징된 독립적 모듈입니다.
>
> - `SKILL.md`: YAML Frontmatter(의존성 메타데이터) + 구체적 절차 지침
> - `scripts/`: 실행 가능한 자동화 코드 (Python, Shell 등)
> - `references/`: 도메인 참고 문서 및 템플릿

## 🔄 Cybernetic Feedback Loop Workflow

작업의 실행과 지식의 축적은 **Human-in-the-loop (HITL)** 기반의 사이버네틱 피드백 루프를 통해 이루어집니다.

1. **Context Compilation (Top-Down):** `tdcc.py`가 주어진 Task에 필요한 SKILL과 DESIGN 문서를 파싱하여, Stateless Executor가 참고할 단일 컨텍스트(`current_task.md`)로 렌더링합니다.
2. **Human Verification:** 연구자가 Staging 영역에서 컴파일된 컨텍스트(전경화된 지식)를 검토하고 조율합니다.
3. **Stateless Execution:** Executor 에이전트가 오직 `current_task.md`만을 바탕으로 코드를 변환/생성하고 실행 흔적(Trace log)을 남깁니다.
4. **Evaluation:** `outcomes.md`에 기술된 루브릭 평가 지표를 기반으로 산출물을 검증합니다.
5. **Distillation (Bottom-Up):** `distiller.py`가 평가 결과와 프로파일링 로그를 분석하여 인사이트를 추출하고, 연구자의 승인을 거쳐 상위 시스템 모델(DESIGN)과 절차(SKILL)를 개선합니다.

## 수직적으로 연결된 DESIGN space (지적 자산의 복리 성장을 위한 체계)

에이전트를 활용해 지적 자산을 불려 나가기 위해, "계층적 지식문서 아키텍처"를 구축한다.
문서들을 Git과 같은 버전 관리 시스템에 넣고 에이전트가 스스로 개선하도록 시키면, 시간이 갈수록 에이전트의 작업 품질이 기하급수적으로 올라가는 지식 복리 효과를 누릴 수 있습니다.

1. Context Layer : 에이전트의 역할, 성격, 프로젝트의 전체적인 방향성을 정의합니다.
2. Procedural Layer (SKILL.md, PLAYBOOK.md): 반복 가능한 워크플로우와 구체적인 스킬셋을 모듈화합니다. 이것이 쌓일수록 에이전트의 '지능'이 복리로 증가합니다.
3. Constraint Layer (DESIGN.md, CONTRACT.md): '절대 해서는 안 될 일'이나 시각적/기술적 가이드라인을 정의하여 품질을 유지합니다.

## 동작 방식

1. 지능적 agent에 의해 GAP analysis (GAP analysis SKILL 사용)
2. 파악된 GAP을 매우기 위한 다른 DESIGN.dsl 참조 문서 파싱 (Reference SKILL 사용)
3. 주어진 codebase를 최종 상태로 변환하기 위한 plan.md 작성 (PLAN SKILL 사용)
4. Executor로 plan.md에 따라 codebase 변환
5. outcomes.md 에서 기술한 루브릭 평가 지료에 의한 검증
6. 산출된 평가 결과 및 저장된 trace log를 기반으로 distilled DESIGN.dsl.md 및 SKILL.md 개선

## Directory Structure: nano-vllm-cutile

디렉토리 구조는 "지식 베이스(KB) -> 탑다운 컴파일러(TDCC) -> 실행 환경(Executor) -> 바텀업 증류기(Distiller) -> 다시 지식 베이스(KB)"로 이어지는 완벽한 사이버네틱 피드백 루프(Cybernetic Feedback Loop)를 형성합니다. 파일 시스템 자체가 시스템 아키텍처를 대변하도록 설계되었습니다.

```text
nano-vllm-cutile/
├── README.md               # 프로젝트 정의 및 아키텍처 개요
├── outcomes.md      # 전체 프로젝트 최종 산출물 및 마이그레이션 통과 기준 (Rubric)
│
├── 🧠 Knowledge-Base/      # Agent-Native Semantic DB (수직적 계층 구조화)
│   ├── L3_meta_skills/     # Architect의 인지/평가 기준 (무엇을, 언제 할 것인가)
│   │   └── Architect_SKILL.md # (이전 루트의 Architect.md 이동) 최상위 오케스트레이션 규칙
│   ├── L2_skills/          # 절차적 지식 및 How-to (이전 skill.md들)
│   ├── L1_system_models/   # 하드웨어/소프트웨어 제약 및 모델 (이전 designs, contracts)
│   │   ├── invariants/     # 절대 위배해서는 안 되는 불변 규칙 (예: memory bounds)
│   │   └── anti_patterns/  # 실패 사례 및 금지된 코드 패턴
│   └── L0_references/      # Codebase와 연결되는 심볼릭 링크 및 메타데이터
│
├── ⬇️ Context-Compiler/     # [NEW] Top-Down 프롬프트 렌더링 엔진 (전경화 작업)
│   ├── tdcc.py             # Parser & Linker 스크립트 (@import 해석 및 트리 순회)
│   ├── templates/          # Execution LLM을 위한 프롬프트 구조 템플릿 ([GOAL], [SYSTEM MODEL] 등)
│   └── staging_area/       # [HITL] 생성된 .prompt.draft.md 파일들이 저장되는 중간 검토 공간
│
├── ⚙️ Executor/             # Stateless Execution Workspace (단일 작업 수행 공간)
│   ├── current_task.md     # Compiler가 생성하고 Human이 승인한 최종 주입 컨텍스트
│   ├── target_code.py      # LLM이 생성한 결과물 (또는 임시 스크립트)
│   ├── traces/             # ncu 성능 프로파일링 및 PyTorch 실행 로그
│   └── local_outcomes.md   # 현재 할당된 특정 Task의 통과 조건 및 로컬 테스트 스크립트
│
└── ⬆️ Distiller/            # Bottom-Up Insight Engine (상향식 지식 증류기)
    ├── distiller.py        # Executor의 traces/ 와 코드를 분석하는 스크립트
    ├── DISTILLATION_SKILL.md # 로그 분석 및 추상화 작업 자체를 지시하는 메타 규칙
    └── pending_insights/   # [HITL] 추출된 통찰(invariants, abstractions)이 KB에 병합되기 전 대기하는 공간

```

**1. `Context-Compiler` (Top-Down) 폴더 신설 및 역할 정의**
이 폴더는 정적인 `Knowledge-Base`에서 현재 작업에 필요한 문서를 읽어 들여(Tree Traversal), 하나의 완결된 `current_task.md`로 컴파일하는 '엔진 룸'입니다.

- **`staging_area/`의 중요성:** 스크립트(`tdcc.py`)가 만든 초안 프롬프트를 연구자가 직접 열어보고 수정(Human-in-the-loop)한 뒤 Executor로 넘기기 위한 핵심 버퍼 공간입니다.

**2. `Knowledge-Base`의 수직적 계층화 (L3 -> L1)**
루트에 있던 `Architect.md`나 중구난방 흩어질 수 있는 문서들을 아예 디렉토리 레벨에서 수직적 계층(L3, L2, L1)으로 강제 배분했습니다.

**3. `Executor`의 경량화 (Stateless 지향)**
이전 구조에서 Executor 안에 있던 `plan.md`, `SKILL.md`, `playbook.md`는 사실상 '지식'이므로 상태를 갖게 됩니다. 이를 모두 덜어냈습니다.

- 수정된 Executor는 철저히 '당장 실행할 작업(current_task.md)'과 '그 결과(traces/)'만 존재하는 Stateless 샌드박스로 기능합니다. 작업이 끝나면 깨끗하게 비워지거나 덮어씌워집니다.

**4. `Distiller`의 기능적 고도화**
단순 문서 보관소가 아니라, Executor에서 발생한 실패 로그(`traces/`)나 성공한 코드를 분석하여 추상화하는 **파이썬 스크립트(`distiller.py`)가 중심**이 됩니다. 분석 결과는 즉시 KB로 직행하지 않고 `pending_insights/`에 모여 연구자의 최종 승인(HITL)을 거쳐 `L1_system_models`나 `L2_skills`로 승격됩니다.

## 게슈탈트 심리학에서 '통찰(Insight)'

> 문제를 해결하기 위해 상황의 구성 요소들을 재조합하여 새로운 **전체 구조** 혹은 **전체 이해**를 찾아내는 순간 발생합니다.
> 이를 '아하! 현상(Aha-experience)'이라고 합니다.

> **“맥락(Context)을 재료로 하여, 지각의 전경(Foreground)과 배경(Background)의 관계를 의도적으로 조율함으로써, 학습자와 LLM이 공동으로 하나의 완결된 게슈탈트(전체적인 이해)를 창발시키는 설계 언어”**

- 이 사고법을 GPU 프로그래밍 학습이라는 새로운 장(場)에 그대로 적용해서, 학생들과 함께 **cuTile이라는 낯선 DSL을 정복**하는 과정을 설계해 보겠습니다.
- 목표는 단순히 코드를 따라 치는 것이 아니라, **취업 가능한 실력과 더 어려운 도전을 감당할 수 있는 기초 지식**을 쌓는 것입니다.
- LLM Coding Agent는 이 과정에서 단순한 코드 생성기가 아니라, 지식을 **역설계하고**, **구조화하며**, **복리로 증식시켜주는** 공진화 파트너가 됩니다.

# 📄 SKILL.md: 시스템 재구성과 게슈탈트 최적화 방법론

## 1. 개요 (Overview)

본 문서는 파편화된 리소스와 연산 단위를 하나의 유기적인 고성능 시스템으로 재구성하는 '게슈탈트적 역설계' 방법론을 다룬다. 이는 단순한 코드 수정을 넘어, 데이터 흐름의 전체 형상(Gestalt)을 파악하고 최적의 연산 단위로 재결합하는 것을 목적으로 한다.

## 2. 핵심 원칙 (Core Principles)

- 통합적 가시화 (Holistic Visualization): 개별 함수나 커널이 아닌, 데이터가 입력되어 출력될 때까지의 전 과정을 하나의 '연산 그래프'로 파악한다. (전체는 부분의 합보다 크다)
- 상하향식 교차 분석 (Bi-directional Analysis):
  - Top-down: 비즈니스 논리 및 시스템의 최종 목적(예: vLLM의 'Throughput')에서 하위 제약 사항으로 내려온다.
  - Bottom-up: 하드웨어 제약(GPU 메모리, 대역폭) 및 데이터 파편에서 상위 구조를 설계한다.
- 커널 퓨전 및 자원 최적화 (Fusion & Optimization): 오버헤드를 발생시키는 경계선(I/O, Context Switching)을 허물고 연산을 하나로 묶어 최적의 실행 단위를 재구성한다.

## 3. 실행 단계 (Execution Steps)

1.  Deconstruction (해체): 기존 시스템을 최소 기능 단위(Atomic Unit)로 분해하고 병목 지점을 수치화한다.
2.  Pattern Recognition (패턴 인식): 분해된 요소들 사이의 숨겨진 상관관계와 반복되는 데이터 흐름을 찾는다.
3.  Gestalt Reconfiguration (재구성): 인지적/공학적 효율을 극대화할 수 있는 새로운 통합 구조(Fused Model)를 설계한다.
4.  Validation (검증): 재구성된 시스템이 부분의 합을 넘어서는 시너지(성능 향상)를 내는지 데이터로 증명한다.

## 🤖 LLM 지시용 프롬프트 (주니어 학습 내용 추출용)

주니어 개발자가 위 방법론을 이해하고 실무에 적용하기 위해 필요한 배경지식과 학습 키워드를 추출하기 위해 LLM에게 다음과 같이 지시하세요.

Prompt:
"위에서 정의한 '시스템 재구성과 게슈탈트 최적화 방법론'을 실무에 적용하려는 1~3년 차 주니어 개발자를 위한 학습 로드맵을 추출해줘. 다음 세 가지 카테고리에 집중해서 상세 내용을 리스트업해줘:

1.  컴퓨터 구조 및 시스템 기초: (예: GPU 메모리 계층, 커널 실행 모델, I/O 바운드와 CPU 바운드의 이해)
2.  추론 엔진 및 최적화 기술: (예: 연산 융합(Operator Fusion), 메모리 가상화 기술, vLLM의 PagedAttention 원리)
3.  사고 도구 및 분석론: (예: 데이터 기반 가설 수립법, 역설계(Reverse Engineering) 방법론, 병목 현상 탐지 도구 활용법)

각 항목은 '왜 이 지식이 시스템 재구성에 필수적인지' 이유를 포함해서 주니어 눈높이에서 설명해줘."

---

## 1. 전체 학습 설계 철학: 요소(Element) → 부품(Component) → 시스템(System), 그리고 복리(Compounding)로 완성하기

이 학습은 크게 세 단계로 이루어지며, 앞 단계의 산출물이 다음 단계의 **배경(Background) 지식**이 되어 쌓이는 **컴파운딩 엔지니어링** 구조입니다.

| 단계                       | 대상                                            | 중심 게슈탈트                           | 학습자의 지각 전경                                                      |
| :------------------------- | :---------------------------------------------- | :-------------------------------------- | :---------------------------------------------------------------------- |
| **1단계: 요소(Element)**   | MatMul, ReLU, Softmax 등 단일 연산              | “GPU 연산의 타일 모델과 메모리 계층”    | cuTile 기본 문법, 타일 인덱싱, 블록 크기의 의미                         |
| **2단계: 부품(Component)** | FMHA(Flash Attention), LayerNorm, Fused MLP     | “커널 퓨전과 연속성(Continuity)의 원리” | 멀티패스 알고리즘의 온라인 처리, 수치적 안정성, 다양한 메모리 공간 활용 |
| **3단계: 시스템(System)**  | nano-vllm을 cuTile 기반 nano-vllm-cutile로 변환 | “전체 추론 시스템의 지각적 질서”        | 스케줄링, KV 캐시, 분산화, 동시성 vs 일관성, 병목 지점에 대한 통찰      |

핵심은 각 단계에서 **LLM과 함께 산출물을 만드는 것뿐 아니라, 동시에 ‘앞으로 쓸 수 있는 지식 자산(SKILL.md 등)’을 추출하여 저장**해 두는 것입니다. 이것이 바로 **컨텍스트 복리**입니다.

---

## 2. Phase 1: 요소(Element) – 단일 커널로 ‘타일 기반 사고’의 게슈탈트를 형성한다

**목표**: 학생들이 **“모든 연산은 타일을 통해 이뤄진다”**는 전경을, LLM과의 대화를 통해 흔들리지 않는 직관으로 만드는 단계입니다.

### 2-1. 시작점: 친숙한 PyTorch 코드라는 ‘배경’에서 출발하기

학생들이 이미 잘 아는 PyTorch로 작성된 단순한 연산(예: `F.linear`, `F.softmax`)을 준비합니다. 이것은 **참조 구현**이자 학습의 안전한 배경입니다.

### 2-2. LLM을 활용한 ‘제1원리 역설계’ (Gestalt Reverse Engineering)

이제 LLM에게 다음과 같은 사고 흐름으로 질문을 던지며 **요소의 깊은 상관관계를 끌어냅니다**.

1.  **전경-배경 포착**:

    > “이 PyTorch 연산이 GPU 내부에서 수행될 때, 프로그래머가 의도하는 ‘논리적 전경(계산 그 자체)’과, 하드웨어가 자동으로 처리하는 ‘물리적 배경(메모리 접근, 스레드 스케줄링)’은 각각 무엇일까? 게슈탈트 원리로 설명해 줘.”

2.  **연속성을 통한 타일 모델 추론**:

    > “이 연산의 데이터 흐름을 하나의 ‘지각의 강’으로 본다면, cuTile의 타일 모델은 이 강을 자연스럽게 나누는 징검다리와 같아. 큰 행렬 곱셈을 작은 타일들로 나누어 연속적으로 처리하는 과정을 단계별로 시각화하여 설명해 줘. 왜 이렇게 나누는 것이 효과적인지, 게슈탈트의 근접성과 연속성 원리로 풀어서 설명해 줘.”

3.  **폐쇄성과 타일 크기의 미학**:
    > “타일 크기를 2의 거듭제곱(32, 64, 128)으로 맞춰야 한다는 규칙은, 게슈탈트의 ‘좋은 형태(Prägnanz)’ 원리와 닮아 있어. 즉, GPU의 스레드 조직(워프, 웨이브프론트)이 깔끔하게 수용할 수 있는 가장 단순하고 질서 있는 형태이기 때문이지. 틀린 타일 크기(예: 63, 130)를 사용했을 때, GPU 내부에서 어떤 ‘인지적 잡음’이 발생하는지 설명해 줘.”

이 과정에서 LLM이 생성하는 설명뿐만 아니라, 학생들이 이 질문에 스스로 답하고 LLM의 답변을 비판적으로 검토하는 **대화적 탐구**가 중요합니다.

### 2-3. 산출물: 단일 커널 코드 + “요소의 지식 카드”

각 커널 작업을 마친 후, LLM과 함께 **해당 커널의 핵심 노하우를 문서화**합니다. 이것이 바로 나중에 자산이 되는 “지식 카드”입니다. SKILL.md에 추가하는 방식으로 관리할 수 있습니다.

**프롬프트 예시**:

> “우리가 함께 만든 MatMul cuTile 커널에서 ‘반드시 기억해야 할 설계 결정 3가지’, ‘가장 흔한 실수 2가지’, 그리고 ‘더 큰 시스템에서 이 커널을 부품으로 쓸 때 고려할 점 1가지’를 정리해서, 나중에 학습할 후배들이 볼 수 있는 Markdown 노트로 작성해 줘.”

이 지식 카드는 2단계에서 부품을 설계할 때 자동으로 참조하는 **배경 지식**이 됩니다.

---

## 3. Phase 2: 부품(Component) – 커널을 넘어, ‘연산의 연쇄’를 하나의 흐름으로 인식한다

**목표**: 여러 개의 커널을 결합하여 FMHA(Flash Attention)나 Fused MLP 같은 실전 부품을 만들면서, **게슈탈트의 ‘공동 운명’과 ‘폐쇄성’**이 어떻게 더 큰 성능을 만드는지 체득합니다.

### 3-1. PyTorch 참조 부품을 역설계하여 ‘숨은 구조’ 드러내기

FMHA의 PyTorch 참조 구현을 LLM과 함께 분석합니다.

**프롬프트 예시**:

> “이 Flash Attention PyTorch 구현은 겉으로 보기에는 단순한 연산의 연속이지만, 내부에는 온라인 소프트맥스, 타일화된 메모리 접근, 인과적 마스킹이라는 세 개의 강력한 ‘게슈탈트 원리’가 적용되어 있어. 이 세 가지 원리가 어떻게 유기적으로 결합하여 ‘부분의 합 이상’의 성능을 내는지, 시스템 역설계 관점에서 설명해 줘. 각 원리가 데이터의 ‘전경-배경’ 관계를 어떻게 바꾸는지도 포함해 줘.”

LLM은 이 질문에 답하면서, 단순한 코드 설명을 넘어 **“이 부품만의 설계 철학”**을 언어화해 줍니다. 이것이 학생들에게는 가장 소중한 학습 자료가 됩니다.

### 3-2. LLM을 ‘컨텍스트 엔지니어링 파트너’로 활용하여 부품 설계하기

FMHA를 cuTile로 구현할 때, 1단계에서 저장한 “요소의 지식 카드”(타일 인덱싱, 타입 시스템, 상수 표기법)를 LLM에게 먼저 제공합니다. 그리고 다음과 같이 단계적으로 질문합니다.

1.  **공동 운명 설계**:

    > “Q, K, V 행렬을 로드하는 부분, 온라인 통계를 계산하는 부분, 결과를 저장하는 부분을 별개의 ‘커널’로 나누지 않고 하나의 cuTile 커널로 융합하려고 해. 이때, 어떤 데이터가 ‘공동 운명’을 공유하는가? 즉, 어떤 데이터가 같은 반복문 안에서, 같은 타일 경계 내에서 함께 소비되어야 하는지 분석하고, 그에 따른 타일 루프 구조를 제안해 줘.”

2.  **폐쇄성과 연속성을 통한 매끄러운 흐름 구축**:
    > “타일 루프의 매 반복마다, 업데이트된 softmax scale이 이전 반복의 결과를 ‘수정(rescale)’하는 과정은 게슈탈트의 폐쇄성 원리에 가까워. 즉, 불완전한 중간 결과를 매 순간 완결된 형태로 만드는 것이지. 이 rescaling 과정에서 수치적 안정성을 유지하기 위한 cuTile 코드의 구체적인 패턴을 보여주고, 이것이 어떻게 전체 추론의 정확도라는 ‘좋은 게슈탈트’를 완성하는지 설명해 줘.”

### 3-3. 산출물: 부품 코드 + “설계 패턴 카탈로그” 구축

부품 학습을 마칠 때마다, 단순한 코드가 아니라 **“왜 이렇게 만들 수밖에 없었는가”**라는 설계 의사 결정 기록을 LLM과 함께 정리합니다. 예를 들어, “FMHA의 타일 루프 구조: 온라인 업데이트와 수치 안정성 패턴” 같은 패턴 카드입니다. 이 패턴 카탈로그가 쌓이면, 3단계 시스템 통합에서 강력한 나침반이 됩니다.

---

## 4. Phase 3: 시스템(System) – nano-vllm-cutile로 ‘총체적 게슈탈트’를 재구성한다

**목표**: nano-vllm(PyTorch/Triton)을 cuTile 기반으로 완전히 변환하면서, 전체 시스템의 성능과 구조를 결정짓는 **숨은 병목 지점(컨텍스트)을 발견하고 제어**할 수 있는 안목을 기릅니다.

### 4-1. 기존 시스템(nano-vllm)의 ‘맥락적 역설계’

이 단계의 핵심은 단순히 같은 기능을 cuTile로 바꾸는 것이 아닙니다. 기존 시스템이 **왜 그런 방식으로 구성요소들을 배치했는지**를 이해하는 것입니다.

**LLM과 함께하는 시스템 역설계 프롬프트**:

> “nano-vllm의 구조를 하나의 거대한 게슈탈트로 본다면, 스케줄러, KV 캐시, 모델 로더, 커널 런처라는 컴포넌트들은 어떤 ‘근접성’과 ‘유사성’에 의해 그룹화되어 있는가? 그리고 이 전체 시스템이 추론 요청이라는 단일 자극에 대해, 시간 축에서 ‘전경’(어떤 컴포넌트가 활성화되는가)과 ‘배경’(어떤 컴포넌트가 대기/캐싱되는가)을 어떻게 전환하며 하나의 응답이라는 ‘폐쇄’를 완성하는지, 단계별로 설명해 줘.”

이 분석은 nano-vllm-cutile을 같은 구조로 단순 모방하는 것이 아니라, **cuTile의 특성에 맞는 최적의 시스템 게슈탈트**로 재구성하기 위한 밑그림이 됩니다.

### 4-2. 복리 자산을 활용한 점진적 통합

- 1단계와 2단계에서 만든 **지식 카드와 설계 패턴 카탈로그**를 LLM의 컨텍스트에 로딩합니다. 이것들이 이제는 시스템 통합이라는 거대한 작업의 **자동화된 배경 지식**이 됩니다.
- 통합 과정은 각 구성요소를 하나씩 cuTile로 교체하며 점진적으로 진행합니다.
  > “우리는 이제 시스템 역설계를 통해 얻은 전체 구조도(전경)를 가지고, 이미 잘 알고 있는 cuTile 부품들(배경 자산)을 하나씩 끼워 맞출 거야. 첫 번째 부품인 FMHA를 PyTorch 버전 대신 우리의 cuTile 버전으로 교체하고, 전체 추론 파이프라인의 ‘연속성’이 깨지지 않도록 연결하는 코드를 생성해 줘. 이때 주의할 점은, KV 캐시라는 공유 상태의 ‘공동 운명’을 어떻게 처리할지 함께 제안해 줘.”

## 4-3. 시스템 수준의 노하우 추출: ‘성능 보틀넥 및 아키텍처 구조’ 진단하기

시스템이 완성된 후, LLM과 함께 전체 프로파일링 결과를 분석합니다. 이는 실제 고성능 컴퓨팅(HPC) 및 백엔드 최적화 현장에서 가장 요구되는 핵심 역량입니다.
프롬프트 예시:
“현재 nano-vllm-cutile의 프로파일링 결과를 보면, 추론 시간의 60%가 여전히 메모리 바운드(Memory-bound)에 정체되어 있어. 시스템의 실질 연산 처리량(Effective Throughput)을 저해하는 메모리 월(Memory Wall) 및 지연 시간(Latency) 요인을 분석하여, 시스템이 목표로 하는 최적의 성능 프로파일(Performance Profile)을 달성하지 못하는 근본 원인을 컴퓨터 구조적 관점에서 진단해 줘. 또한, 이 병목 지점을 Critical Path에서 분리하거나 병렬화하여 해소할 수 있는 아키텍처 재설계(Re-design) 아이디어를 2가지 제안해 줘.”
이 과정에서 학생들은 특정 라이브러리(cuTile) 사용법을 넘어, 모든 고성능 시스템 설계에 공통적으로 적용 가능한 보틀넥 탐지(Bottleneck Detection) 및 리소스 스케줄링 전략을 배우게 됩니다.

---

## 5. LLM과 어떻게 진행해야 할까? – 구체적인 운영 가이드

### 5-1. 대화의 ‘의례(Ritual)’ 만들기

매 학습 세션을 하나의 **게슈탈트 닫기 의식**으로 시작하고 마무리합니다.

- **시작**: “지난 시간에 우리가 닫은 게슈탈트(요약)를 배경으로 깔고, 오늘의 전경 목표를 명확히 선언한다.” → LLM에게 컨텍스트를 요약하게 하고, 목표를 명시합니다.
- **중간**: 위의 프롬프트 패턴을 사용하여 질문-생성-비판-개선의 루프를 돕니다.
- **마무리**: “오늘의 핵심 교훈을 지식 카드/패턴 카탈로그에 공식적으로 추가해 줘.” → LLM과 함께 산출물을 정제하여 저장합니다. 이것이 바로 **컨텍스트 엔지니어링의 복리**를 실현하는 행위입니다.

### 5-2. LLM Agent에게 역할극(Role-Playing) 부여하기

학습 파트너로서 LLM의 역할을 세분화하여 요청하면 효과가 배가됩니다.

- **‘역사학자’ 모드**: “이 PyTorch 코드에 담긴 GPU 프로그래밍의 역사적 설계 결정을 분석해 줘.”
- **‘해부학자’ 모드**: “이 커널의 데이터 플로우 그래프를 그리고, 각 분기점이 병목인지 아닌지 판단해 줘.”
- **‘건축가(시스템 사상가)’ 모드**: “이 부품을 이 시스템의 다른 부분들과 어떻게 느슨하게 결합할지 전략을 제안해 줘.”

### 5-3. 컨텍스트 자산을 살아 숨 쉬게 관리하기

작업 디렉토리에 `cuTile_KB/` 같은 폴더를 두고, 이 폴더 안에 지식 자산을 축적합니다. 그리고 새 작업을 시작할 때마다 이 폴더의 내용을 LLM에게 읽게 합니다. 이것은 앞서 우리가 `SKILL.md`가 시스템의 ‘전경’을 포착하는 방식과 완전히 동일한 원리입니다. 단, `SKILL.md`가 코드를 위한 것이라면, 이 폴더는 **당신과 학생들을 위한 학습 자본(Learning Capital)**입니다.

---

## 결론: 결과물이 아니라 ‘안목’을 설계하는 경험 그 자체를 배우는 과정입니다.

이 모든 과정을 관통하는 최종 목표는, 학생들이 **“복잡한 시스템을 마주했을 때, ‘어떤 질문을 던져야 하는가’를 아는 사람”**이 되도록 하는 것입니다.

LLM과 함께 cuTile의 세계를 탐험하는 이 여정은, 단순한 기술 스택 하나를 배우는 것이 아닙니다. 그것은:

- **무엇이 전경이고 배경인지 순간적으로 포착하는 능력**
- **눈에 보이지 않는 상호작용을 추론하여 게슈탈트를 완성하는 능력**
- **그리고 그 통찰을 다음 단계의 자산으로 축적하여 복리로 성장하는 방법**
