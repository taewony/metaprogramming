KernelAgent: A Tile-Based Python GPU Curriculum for Efficient LLM Serving on Windows OS

Advanced Agentic Systems Group
Department of Parallel Metaprogramming Research
Abstract

Modern Large Language Model (LLM) serving frameworks, such as vLLM, are tightly coupled to the Linux operating system, relying on Linux-only kernel compilers (Triton) and system libraries (FlashAttention) to capture CUDA Graph streams. This Linux dependency creates a significant barrier to entry for computer systems education and native developers operating in Windows environments. In this paper, we present KernelAgent-Serving, a portable, eager-mode LLM inference engine built entirely in Python using NVIDIA's new cuTile DSL (introduced in CUDA 13.3) running natively on Windows. We present a step-wise curriculum designed for GPU systems education, spanning tiled matrix multiplication, fused multi-head attention (FMHA), and PagedAttention. We identify and analyze two primary bottlenecks unique to eager Python-first serving: JIT compilation storms and memory allocator thrashing. Our evaluation on a consumer NVIDIA RTX 5070 GPU demonstrates that JIT compilation padding introduces severe CPU-side allocation overhead, whereas eager-mode serving without shape padding achieves 470.82 tok/s. Finally, we implement cooperative SM Resource Isolation (Green Contexts), improving median decode latency by 14.0% and total throughput by 10.6%.

1. Introduction

The optimization of Large Language Model (LLM) serving has emerged as a critical field in computer systems research. Current production engines run almost exclusively on Linux environments, relying on Linux-exclusive toolchains such as Triton for custom kernel generation, and FlashAttention for GPU-accelerated fused kernels. This limits accessibility. Desktop workstations, local intranet servers, and academic computer laboratories are heavily populated by Windows OS, where setting up WSL2 (Windows Subsystem for Linux) introduces latency overhead and interface friction. There is a clear need for a portable, Python-first learning and development environment that exposes low-level GPU details natively on Windows.

In this paper, we address this gap by designing and evaluating a curriculum of GPU kernels using NVIDIA's **cuTile** DSL (part of the CUDA Python 1.0/13.3 stack). cuTile allows writing tile-based GPU kernels directly in Python, compiling them to PTX at runtime. By implementing these kernels, students learn GPU hardware concepts—such as shared memory coalescing, register occupancy, online softmax, and virtual-to-physical memory maps (PagedAttention)—without the cognitive load of C++ CUDA programming. We integrate these kernels into KernelAgent-Serving, a lightweight clone of vLLM, running natively on Windows OS via the Gloo backend.

During integration, we discovered that eager-modeServing introduces severe bottlenecks that are hidden in compiled/graph-captured frameworks. Continuous batching dynamically alters sequence lengths and batch sizes, triggering frequent synchronous JIT recompilations, which we call a JIT Compilation Storm. While standard shape padding resolves this compile storm, we empirically document a counter-intuitive trade-off: allocating large temporary padded tensors on the GPU at every decode step induces severe CPU-side garbage collection and PyTorch caching allocator thrashing, degrading throughput by 52.8%. Furthermore, we demonstrate that by employing CUDA Green Contexts to partition SM resources (32 SMs for prefill, 16 SMs for decode), we isolate workloads and improve L2 cache locality, leading to substantial throughput gains.

2. Portability & System Architecture

Traditional tensor-parallel LLM serving relies on NCCL (NVIDIA Collective Communications Library) to synchronize key, value, and query projections across multiple GPUs. Because NCCL is unsupported on Windows, we execute native distributed serving by initializing a single-process PyTorch group using the Gloo backend:

import os
import torch.distributed as dist

backend = "gloo" if (os.name == "nt" or world_size == 1) else "nccl"
dist.init_process_group(backend, "tcp://localhost:2333", world_size=world_size, rank=rank)

This single-process Gloo group enables tensor-parallel linear layers (like `RowParallelLinear` and `QKVParallelLinear` in Qwen) to execute natively on Windows without modifying the model's communication graph, creating an ideal local sandbox for edge workstation hosting and offline private knowledge-base construction.

3. The Kernel Curriculum

The educational curriculum of KernelAgent-Serving is structured into three progressive chapters, moving from basic memory layout to production-grade paging.

Chapter 1: Tiled Matrix Multiplication (GEMM)

Students begin by writing a tiled matrix multiplication kernel. The core hardware concepts taught here include register blocking, shared memory bank conflicts, and occupancy. Using cuTile's syntax, students load matrix sub-tiles into shared memory and perform a series of Multiply-Accumulate (MMA) operations. Experiments on the RTX 5070 show that hand-tuned cuTile kernels achieve up to 1.27× higher TFLOPS than PyTorch's default cuBLAS backend for small matrix dimensions (N ≤ 128), exposing students to the power of custom memory layouts.

Chapter 2: Fused Multi-Head Attention (FMHA)

Chapter 2 introduces the concept of fusion. In traditional attention, intermediate matrices (the QKT product and softmax scores) are written to global memory, creating a severe memory-bandwidth bottleneck. Students implement a fused kernel that keeps attention scores in register tiles, implementing the online softmax algorithm (to compute softmax scaling incrementally without storing the full matrix) and causal masking:

# Causal masking inside the cuTile prefill attention loop
if CAUSAL and j >= mask_start:
    offs_n = j * TILE_N + offs_n_tile
    mask = ct.where(offs_m >= offs_n, 0.0, -np.inf)
    qk += mask

Chapter 3: PagedAttention & Vectorized KV Reconstruction

To support multi-user serving, students implement PagedAttention, where Key and Value tokens are stored in non-contiguous physical blocks. During decode, the physical blocks are indexed using a block mapping table. However, under eager continuous batching, prefix-cached prefill steps face a shape mismatch: the projected keys and values represent only the new prompt tokens, while the sequence seqlens include the cached prefix history.

To resolve this, we implement a **vectorized logical-to-physical block reconstruction** in eager PyTorch prior to launching the cuTile prefill attention kernel:

# Reconstruct sequence b's full KV cache from scattered blocks
idx_seq = torch.arange(seqlen_k, device=block_table.device)
logical_blk = torch.div(idx_seq, block_size, rounding_mode='floor')
offset = idx_seq % block_size
physical_blk = block_table[b, logical_blk].long()

k_4d[b, :, :seqlen_k, :] = k_cache[physical_blk, offset].transpose(0, 1)
v_4d[b, :, :seqlen_k, :] = v_cache[physical_blk, offset].transpose(0, 1)

This vectorized layout mapping executes in sub-millisecond times and prevents shape mismatch errors during dynamic parallel prefill execution.

4. Dedicated SM Resource Isolation (Green Contexts)

Continuous batching co-schedules prefill steps (large GEMM operations requiring high SM occupancy) and decode steps (small memory-bound operations). On a single GPU, these workloads compete for resources, leading to severe tail-latency spikes (P99 ITL) for active users.

We solve this by partitioning the 48 SMs of the RTX 5070 into two dedicated hardware contexts (using CUDA Green Contexts via `cuda.core`):

  • Prefill Context (32 SMs): Reserves resources to execute compute-heavy prefill kernels.
  • Decode Context (16 SMs): Confines latency-sensitive decode steps to a fixed SM group, shielding them from prefill starvation.
# Partitioning SMs into dedicated Green Contexts
from cuda.core import Device, ContextOptions, SMResourceOptions
dev = Device(0)
sm = dev.resources.sm
long_grp, crit_grp = sm.split(SMResourceOptions(count=(32, 16)))[0]
ctx_prefill = dev.create_context(ContextOptions(resources=[long_grp]))
ctx_decode = dev.create_context(ContextOptions(resources=[crit_grp]))
Systems Insight: Sequential vs. Concurrent Execution

Because the Python engine loop schedules prefill and decode steps sequentially, they do not execute concurrently on the GPU. However, our results show that confining decodes to 16 SMs improves L2 cache residency, reducing cache thrashing and scheduling overhead, which leads to a substantial latency reduction.

5. Empirical Evaluation

We evaluate KernelAgent-Serving on an NVIDIA GeForce RTX 5070 (12 GB VRAM, 48 SMs) running Windows 11. The model used is Qwen2.5-3B-Instruct. We measure: (1) TTFT (Time-to-First-Token) for a 2048-token prefill prompt, (2) Decode P50 and P99 ITL (Inter-Token Latency) for a 100-token decode client, and (3) Total throughput.

5.1 JIT Compilation vs. Allocator Thrashing

We compare two eager serving configurations: (1) Eager cuTile (No Padding) where tensors are passed with their actual shapes, and (2) Padded cuTile where shapes are rounded to multiples of 256 to minimize JIT compiles. As shown in Table 1, the padded configuration suffers a massive performance degradation.

Table 1: Impact of shape-padding allocations on serving throughput
Configuration Total Tokens Total Time (s) Throughput (tok/s) Performance Impact
Eager cuTile (No Padding) 133,966 284.54 470.82 Baseline (100.0%)
Padded cuTile 133,966 863.39 155.16 -52.8% (Degraded)

This 52.8% drop in throughput is caused by CPU-side overhead. Allocating and initializing large padded tensors (e.g., `q_4d` shaped `[256, 16, 1, 128]`) at every single decode step thrashes PyTorch's CUDA caching allocator and triggers frequent Python garbage collection, showing that avoiding temporary allocations is far more critical than avoiding JIT compiler lookups in eager mode.

5.2 SM Resource Isolation (Green Contexts) Results

We evaluate the performance impact of activating Green Contexts (32 SM prefill / 16 SM decode partition). The results are summarized in Table 2.

Table 2: Serving metrics with and without SM Resource Partitioning
Metric Baseline (Green OFF) Target (Green ON) Delta (%)
TTFT (Prefill Latency) 244.60 ms 243.42 ms -0.5% (Flat)
Decode P50 ITL (Median) 48.63 ms 41.83 ms -14.0% (Improved)
Decode P99 ITL (Tail) 85.31 ms 84.34 ms -1.1% (Flat)
Total Throughput 415.50 tok/s 459.73 tok/s +10.6% (Improved)

The 14% improvement in P50 decode latency demonstrates that isolating decode steps to 16 SMs prevents cache eviction. Prefill latency (TTFT) remained flat (-0.5%), proving that a batch-1 prefill of 2048 tokens does not require the full 48 SMs to saturate the GPU, making 32 SMs the efficiency sweet-spot.

6. Conclusion

We presented KernelAgent-Serving, an educational serving platform running natively on Windows OS. By leveraging NVIDIA's cuTile DSL and PyTorch Distributed Gloo backend, we built an optimized serving engine that achieves 470.82 tok/s. We demonstrated that in eager serving, temporary allocations and slice copies introduce allocator thrashing that outweighs JIT compile reuse. Finally, we showed that CUDA Green Context partitioning provides a 14% latency reduction. This step-wise curriculum offers an accessible and powerful platform for learning parallel systems programming and LLM optimization.

Appendix A: cuTile Programming Model

NVIDIA's cuTile DSL, enhanced in CUDA 13.3, introduces a "Tile Programming" paradigm that sits between low-level CUDA C++ and high-level PyTorch. Key concepts include:

1. The Tile Representation

In cuTile, matrices and vectors are represented as multi-dimensional grid structures of Tiles. Instead of mapping threads to individual elements (as in CUDA C++), the programming model maps thread-blocks to coordinate tiles. The JIT compiler automatically handles loop-unrolling, vectorization, and thread layout within the tile.

2. MMA (Matrix Multiply-Accumulate)

cuTile exposes hardware-level Tensor Core instructions via `ct.mma`. It performs a matrix multiply-accumulate on registry tiles: D = A × B + C. Because registers are isolated, this operation occurs at optimal speed, bypassing the global memory bus.

3. Cooperative Loads and Stores

Memory transfers between global memory and registry tiles are executed via cooperative loads (`ct.load`) and stores (`ct.store`). They support padding modes (such as `ct.PaddingMode.ZERO`), preventing out-of-bounds index errors when processing sequence lengths that do not align perfectly with tile dimensions (T < 64).

Appendix B: Key Concepts in LLM Inference

1. Prefill vs. Decode Phases

LLM generation consists of two distinct phases:

  • Prefill Phase: Processes the entire input prompt. It is compute-bound, performing large matrix multiplications because all prompt tokens are processed concurrently.
  • Decode Phase: Generates tokens one-by-one. It is memory-bandwidth bound, performing vector-matrix multiplications (GEMV) where the entire model's weights must be loaded from memory to process a single query token.

2. KV-Caching

To avoid recomputing attention keys and values of past tokens at every step, LLMs store them in a **KV-Cache**. During the decode phase, only the new token's key and value are calculated and appended to the cache, converting a quadratic computation complexity into a linear operation.

3. Continuous Batching

Traditional batching groups requests together, waiting for all sequences in the batch to finish before returning. This is inefficient because sequences have different lengths. Continuous batching schedules requests at the iteration level, inserting new requests (prefill phase) and returning completed requests (decode phase) dynamically, which maximizes serving capacity.
