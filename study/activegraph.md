ActiveGraph의 타입 시스템은 크게 **프레임워크가 정의하는 부분**과 **개발자가 정의하는 부분**으로 나뉩니다. 이 둘을 이해하는 것이 이 시스템의 핵심입니다.

### 1. 프레임워크 정의 타입: 이벤트 타입 (Event Types)

이것은 시스템이 "무슨 일이 일어났는지"를 말하기 위해 미리 정해둔 **고정된 단어**입니다. 예를 들어, 새로운 데이터가 추가되면 `object.created`, 뭔가 처리 중이면 `behavior.started` 같은 이벤트가 발생합니다. 시스템은 이 타입들을 보고 다음에 어떤 행동을 할지 결정합니다.

### 2. 개발자 정의 타입 1: 객체 타입 (Object Types)

이것은 여러분이 "무슨 종류의 데이터인지"를 정하는 **자유로운 이름표**입니다. `graph.add_object()` 함수를 쓸 때 원하는 아무 문자열이나 타입으로 지정할 수 있습니다.

*   예를 들어, `"claim"` (주장), `"memo"` (메모), `"topic"` (주제) 같은 이름을 붙일 수 있습니다.
*   **중요한 점은**, 이 타입을 사용하기 위해 꼭 어딘가에 미리 등록하거나 복잡한 스키마를 정의할 필요가 없다는 것입니다. 마치 자유롭게 포스트잇에 이름을 붙이는 것과 같습니다.
*   그래도 검증이 필요하다면, 선택적으로 `Pack` 이라는 단위로 묶어 Pydantic 스키마를 추가할 수 있습니다.

### 3. 개발자 정의 타입 2: 관계 타입 (Relation Types)

객체와 객체 사이의 연결이 "무슨 관계인지"를 나타내는 이름표입니다. `graph.add_relation(출발객체, 도착객체, 타입)` 형태로 사용합니다.

*   예를 들어, `"supports"` (지지한다), `"contradicts"` (모순된다), `"depends_on"` (의존한다) 같은 이름을 붙일 수 있습니다.
*   객체 타입과 마찬가지로 중앙에 등록할 필요 없이 자유롭게 사용할 수 있습니다.
*   `Pack`을 통해 연결할 수 있는 객체의 종류를 제한하는 규칙을 추가할 수도 있습니다.

### 이 세 가지가 어떻게 함께 동작하는지

이해를 돕기 위해 하나의 예시를 따라가 보겠습니다.

1.  **운영자**가 시스템에 `goal.created`라는 **프레임워크 이벤트**를 보냅니다 (예: "조사 시작").
2.  이 이벤트를 구독하고 있던 **행동(Behavior)**이 실행되어, `graph.add_object("topic", ...)` 코드를 통해 **개발자 타입**인 `"topic"` 객체를 생성합니다.
3.  이 생성 행위로 인해 시스템은 `object.created`라는 **프레임워크 이벤트**를 자동으로 발생시킵니다. 이 이벤트에는 방금 만든 `"topic"` 객체의 정보가 담겨 있습니다.
4.  이번에는 `object.created` 이벤트 중에서 `type="topic"`인 경우에만 반응하도록 설정된 다른 **행동**이 실행됩니다. 이 행동은 `tool.requested` 같은 **프레임워크 이벤트**를 발생시켜 외부 검색을 수행할 수도 있습니다.

이처럼 **프레임워크는 사건의 '흐름'을** 제공하고, **개발자는 그 흐름 속에서 다룰 '데이터의 종류'를** 정의합니다. 이 두 가지가 서로 맞물려 시스템이 동작하는 것입니다.

### 핵심 디자인 철학: 스키마보다는 타입

ActiveGraph는 전통적인 데이터베이스처럼 모든 데이터의 모양을 강제하는 중앙 스키마보다는, **이 타입 시스템을 통해 유연성을 추구**합니다.

*   **타입은 데이터에 붙은 이름표**입니다. 무슨 역할을 하는지 나타내는 명사여야 합니다 (예: `claim`, `evidence`).
*   **관계는 동작이나 상태를 나타내는 동사**여야 합니다 (예: `supports`, `contradicts`).
*   이렇게 정의된 타입 자체가 소비자(행동)와의 계약 역할을 합니다. 특정 타입에 반응하는 행동은 그 타입이 가진 의미를 신뢰하고 데이터를 처리합니다.
*   이 방식의 장점은 도메인 지식이 진화할 때 **일일이 마이그레이션 스크립트를 작성하지 않고도** 새로운 타입을 추가하거나 기존 타입의 의미를 확장할 수 있다는 점입니다.

### 실제 사용 예시: 딜리전스 팩 (Diligence Pack)

이러한 설계 방식의 좋은 예로, 문서에 소개된 '딜리전스(Diligence) 팩'을 들 수 있습니다. 이 팩은 회사 실사(Diligence) 작업을 위해 만들어진 구체적인 타입 모음입니다.

*   **객체 타입 (8개)**: `company` (회사), `document` (문서), `question` (질문), `claim` (주장), `evidence` (증거) 등.
*   **관계 타입 (6개)**: `supports` (증거가 주장을 지지함), `contradicts` (두 주장이 모순됨), `addresses` (주장이 질문을 다룸) 등.

이 타입들은 작은 규모(8~15개)로 유지되어, 시스템이 명확하게 동작하도록 돕습니다. 이는 '무엇이든 표현하려다 오히려 아무것도 표현하지 못하는' 상황을 피하기 위한 설계 원칙입니다.

대학의 AX융합교육과정 설계를 위해 ActiveGraph를 활용하는 것은 매우 적절한 접근 방식입니다. ActiveGraph는 **이벤트 소싱 기반의 그래프 런타임**으로, 복잡한 데이터 수집, 가공, 생성 과정을 **감사 가능하고 재현 가능한 워크플로우**로 설계할 수 있게 해줍니다.

여러분의 요구사항(기본 데이터 파일 수집 → 내용 요약(Digest) → 새로운 파일 작성)을 ActiveGraph의 타입 시스템과 행동(Behavior) 개념에 맞춰 설계하는 전체적인 가이드를 제시합니다.

### 1. 핵심 설계 철학: 데이터는 '객체', 과정은 '관계'와 '행동'으로

ActiveGraph의 타입 시스템은 **유연성**을 핵심으로 합니다. 전통적인 데이터베이스처럼 엄격한 스키마를 강제하기보다는, 데이터에 **의미 있는 이름표(타입)** 를 붙이고, 이 타입을 기반으로 **행동(Behavior)** 이 반응하도록 설계하는 것이 핵심입니다.

따라서 교육과정 설계에 필요한 모든 데이터 조각(파일, 요약본, 설계 요소 등)은 `graph.add_object()`로 **객체(Object)** 로 만들고, 객체 간의 관계는 `graph.add_relation()`으로 **관계(Relation)** 로 정의합니다. 그리고 이러한 객체와 관계의 생성 및 변화를 주도하는 로직은 **행동(Behavior)** 으로 구현합니다.

### 2. 단계별 ActiveGraph 구성 가이드

#### 1단계: 교육과정 설계를 위한 타입 시스템 정의

가장 먼저, 여러분의 업무 도메인에 맞는 **객체 타입(Object Types)** 과 **관계 타입(Relation Types)** 을 정의해야 합니다. 이는 마치 프로젝트의 '데이터 사전'을 만드는 것과 같습니다.

*   **객체 타입 (Object Types)**: 다룰 데이터의 종류를 나타내는 명사형 타입입니다.
    *   `SourceDocument`: 수집한 원본 데이터 파일 (PDF, HWP, Excel 등)
    *   `Digest`: 원본 파일의 내용을 요약한 결과물
    *   `CurriculumComponent`: 교육과정의 구성 요소 (교과목, 학습목표, 역량 등)
    *   `DraftDocument`: 최종적으로 작성될 새로운 설계 파일

*   **관계 타입 (Relation Types)**: 객체 간의 연결 관계를 나타내는 동사형 타입입니다.
    *   `has_digest`: (SourceDocument) --has_digest--> (Digest)
    *   `informs`: (Digest) --informs--> (CurriculumComponent)
    *   `composes`: (CurriculumComponent) --composes--> (DraftDocument)

이러한 타입들은 `Pack`이라는 단위로 묶어 관리할 수 있으며, 필요한 경우 Pydantic 스키마를 추가하여 데이터의 형식을 검증할 수도 있습니다. 예를 들어, `CurriculumDesignPack`을 만들어 관련 타입들을 그룹화할 수 있습니다.

#### 2단계: 데이터 수집 및 요약 워크플로우 설계

이제 정의한 타입을 바탕으로 실제 작업을 수행할 **행동(Behavior)** 을 설계합니다.

1.  **데이터 수집 행동 (Data Ingestion Behavior)**
    *   **역할**: 지정된 디렉토리나 소스에서 기본 데이터 파일을 읽어들입니다.
    *   **동작**:
        *   각 파일을 읽어 `SourceDocument` 타입의 객체를 생성합니다. (`graph.add_object("SourceDocument", {"name": file_name, "content": file_content, ...})`)
        *   파일 수집이 완료되면, `ingestion.completed` 와 같은 **프레임워크 이벤트**를 발생시켜 다음 단계를 트리거합니다.

2.  **내용 요약 행동 (Digestion Behavior)**
    *   **역할**: `SourceDocument` 객체를 분석하여 요약본(Digest)을 생성합니다.
    *   **동작**:
        *   `object.created` 이벤트 중에서 `type="SourceDocument"`인 경우를 구독합니다.
        *   해당 문서의 내용을 LLM 등을 활용해 요약합니다.
        *   요약 결과로 `Digest` 타입의 객체를 생성합니다. (`graph.add_object("Digest", {"summary": summary_text, ...})`)
        *   원본 문서와 요약본의 관계를 정의합니다. (`graph.add_relation(source_doc.id, digest.id, "has_digest")`)
        *   요약이 완료되면 `digestion.completed` 이벤트를 발생시킵니다.

#### 3단계: 종합 및 신규 파일 작성 워크플로우 설계

수집되고 요약된 정보를 바탕으로 최종 설계 파일을 작성하는 단계입니다.

1.  **교육과정 설계 행동 (Curriculum Design Behavior)**
    *   **역할**: 여러 `Digest` 객체를 종합하여 교육과정의 구성 요소를 도출하고, 이를 바탕으로 최종 설계 파일을 작성합니다.
    *   **동작**:
        *   `digestion.completed` 이벤트를 구독하거나, 특정 조건(예: 모든 문서 요약 완료)이 충족되면 실행됩니다.
        *   모든 `Digest` 객체를 조회하여 핵심 주제, 필요한 역량, 교과목 등을 추출합니다.
        *   추출된 각 요소를 `CurriculumComponent` 타입의 객체로 생성합니다.
        *   `CurriculumComponent` 객체들과의 관계를 설정합니다. (예: `Digest`가 어떤 `CurriculumComponent`를 '제안(informs)'했는지)
        *   도출된 구성 요소를 종합하여 최종 설계 문서의 초안을 작성하고, 이를 `DraftDocument` 타입의 객체로 저장합니다.
        *   필요에 따라 `DraftDocument`의 내용을 실제 파일(예: Markdown, PDF)로 내보내는 행동을 추가로 연결할 수 있습니다.

### 3. 실제 구현 시 참고할 점

*   **예제 코드 참고**: ActiveGraph의 `examples` 디렉토리에 있는 `llm_claim_extraction.py`나 `diligence_with_tools.py`는 데이터를 읽고, 처리하고, 새로운 객체를 생성하는 유사한 워크플로우를 구현한 좋은 참고 자료가 될 것입니다.
*   **이벤트 기반 설계**: 각 행동은 특정 이벤트에 반응하도록 설계하는 것이 중요합니다. 이를 통해 각 단계가 독립적이고, 재사용 가능하며, 전체 프로세스를 감사 가능하게 만들 수 있습니다.
*   **점진적 개발**: 처음부터 완벽한 시스템을 만들기보다는, "파일 읽기 → 요약하기" 같은 핵심 루프를 먼저 구현하고, 점차 세부 설계 행동을 추가해 나가는 것을 추천합니다.
*   **선택적 검증**: 객체에 저장되는 데이터의 형식이 중요하다면, `Pack`을 정의할 때 Pydantic 스키마를 함께 명시하여 데이터 무결성을 확보할 수 있습니다.

이 가이드를 바탕으로 ActiveGraph의 유연한 타입 시스템과 강력한 이벤트 기반 아키텍처를 활용하여, 여러분의 AX융합교육과정 설계 과정을 체계적이고 효율적으로 자동화할 수 있을 것입니다.
